01 · QUICK START

Connect, simulate, inspect, sign.

  1. Open the wallet chooser.Select a discovered browser wallet or WalletConnect when configured.
  2. Switch to Robinhood Chain.Verity requests chain ID 4663 and checks it again before signing.
  3. Request a simulation.The server quotes only the pinned ETH → USDG path and never broadcasts.
  4. Review every field.Recipient, router, value, minimum output, fee tier, gas, deadline, block, and calldata remain visible.
  5. Approve in your wallet.Your wallet is the only signer. A transaction hash means broadcast, not success.

03 · EXECUTION LIFECYCLE

Every state remains distinct.

intent
→ quote
→ exact on-chain simulation
→ user review
→ local wallet signature
→ broadcast
→ pending
→ receipt-confirmed | reverted | unknown

Account, chain, provider, or quote freshness changes invalidate the prepared execution. A transaction hash is not success. Verity requires a successful Robinhood Chain receipt before showing confirmed.

04 · SECURITY BOUNDARY

Fail closed before the wallet prompt.

No key custody

No seed phrase, private key, server signer, relayer signer, or recovery credential.

Pinned route

One Uniswap v4 Universal Router, PoolManager, PoolKey, fee, tick spacing, zero hook, recipient policy, and native value relationship.

Calldata verification

The browser recursively decodes and canonically re-encodes Universal Router execute, the single V4_SWAP command, and the exact action sequence SWAP_EXACT_IN_SINGLE → SETTLE_ALL → TAKE_ALL.

Bounded intent

Maximum 1 ETH, slippage 0.10–5.00%, short quote lifetime, and on-chain deadline.

Single flight

A synchronous execution lock prevents duplicate wallet submission prompts.

Settlement truth

Pending, confirmed, reverted, and unknown are never collapsed into one success state.

05 · RECEIPT JOURNAL

Evidence retained in your browser.

The execution journal begins only after a wallet returns a canonical transaction hash. It records quote evidence, broadcast time, provider class, simulated block, and later receipt state.

  • Coverage is explicitly browser-local, capped at 50 entries.
  • Reloading the same browser preserves the journal best-effort.
  • JSON export uses evidence schema v2. Existing v1 browser-local entries remain readable and new entries are stored under the v2 key.
  • A shareable receipt URL verifies the public transaction hash through the chain-pinned receipt API.
  • Local storage is not a durable multi-device database and must not be treated as one.

07 · API REFERENCE

Same-origin, no-store endpoints.

GET /api/health

Chain/provider status and non-custodial execution scope.

GET /api/config

Pinned chain, token, router, pool, fee, and input constraints.

GET /api/markets

Source-scoped v4.fun identities plus canonical PoolManager evidence, with explicit partial and provider-unavailable coverage.

POST /api/market-quote

Read-only V4Quoter liquidity evidence for a canonical PoolKey. It returns no router target, calldata, approval, minimum output, signature, or broadcast path.

POST /api/quote

Fresh constrained quote, simulation evidence, gas estimate, and exact calldata. Never broadcasts.

GET /api/receipt?hash=0x…

Returns pending, confirmed, reverted, unknown, or provider-unavailable truth.

Unsupported methods fail with 405. Provider failure returns an explicit unavailable/error state instead of fabricated values.

08 · LIMITATIONS

What Verity does not claim.

  • The public Robinhood RPC is rate-limited and is not sufficient as the sole provider for broad launch.
  • Market indexing is partial while Blockscout coverage has a gap between the certified historical prefix and bounded recent window. Discovery is never treated as execution approval.
  • Generic market probes are quote-only. Multi-token execution remains blocked until token behavior, hook registry/runtime, authorization, and settlement semantics are verified.
  • The current API limiter is per warm runtime instance, not distributed global WAF enforcement.
  • Simulation is expected behavior at a specific chain state, not a guarantee.
  • A successful chain receipt is not a claim of full Ethereum finality.
  • Replacement and reorg handling remain incomplete.
  • The mainnet execution loop is not marked verified until a user-approved small transaction receives a successful receipt.
  • Stock Token/RWA execution, unattended copytrading, server-held session keys, and global-jurisdiction claims are excluded.
